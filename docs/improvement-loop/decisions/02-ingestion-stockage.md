# Décision 02 — Ingestion et stockage des observations Copilot CLI

**Statut :** décision d'architecture proposée, à éprouver sur le pilote local avant tout déploiement collectif. **Périmètre :** le canal supplémentaire de la boucle d'amélioration, depuis les sessions de Copilot CLI exécutées dans des dépôts de code jusqu'aux observations consultables par le coach. « agent-repo » est un nom fictif pour la source des `SKILL.md` et `*.agent.md` installés volontairement sous `~/.copilot` ; ce n'est ni le répertoire habituel des sessions, ni un magasin de données. Nous n'avons accès ni à ce dépôt réel, ni aux postes, ni aux règles internes de l'organisation.

## Décision

1. **Phase 0, un utilisateur :** un hook personnel signale les changements de session à un travailleur local. Celui-ci lit la source native sur le poste, vérifie le périmètre autorisé, normalise et filtre, puis écrit **uniquement l'observation filtrée** dans une file d'export locale chiffrée. Un journal de travaux, chiffré lui aussi, peut contenir temporairement un pointeur vers la source. Il n'y a pas d'export réseau automatique. Les extraits de niveau 2 restent dans un espace local distinct de l'index ; le niveau 3 (transcription intégrale) est exclu du pilote.
2. **Phase 4, plusieurs utilisateurs, après décision de sécurité et conformité :** le même format filtré part par HTTPS vers une API d'ingestion dédiée. L'API authentifie la personne, impose le périmètre, attribue les identifiants de tenant, équipe et utilisateur, puis sépare les métadonnées structurées des extraits dans deux magasins. La livraison est au moins une fois ; une clé d'idempotence et une contrainte unique donnent un effet unique par révision.
3. **GitHub ne reçoit que le code, les schémas, des cas synthétiques et des résultats agrégés autorisés.** Ni dépôt Git, ni issue/PR, ni GitHub Actions, ni artefact ou journal de CI ne servent de transport ou de magasin aux transcriptions et jeux d'évaluation sensibles.

Ce canal ne change pas la rétention ou la synchronisation natives de Copilot. GitHub documente des transcriptions complètes locales sous `~/.copilot/session-state/`, un SQLite local partiel, une synchronisation éventuelle vers le **compte personnel** et l'absence d'accès administratif automatique aux sessions synchronisées. Il faut donc un collecteur sur chaque poste inclus dans le périmètre ; le SQLite de Copilot n'est pas notre base d'export. [Source : données de session GitHub Copilot](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/session-data).

## Frontières de confiance et flux

| Zone | Données et droits | Sortie permise |
| --- | --- | --- |
| Session native Copilot, sur le poste | Prompts, réponses, outils, fichiers et identifiants potentiellement sensibles ; éventuellement synchronisés par Copilot selon sa politique propre | Lecture locale par le collecteur seulement, si session et dépôt admissibles |
| Collecteur et file du poste | Pointeur transitoire vers la source native, règles locales, observations filtrées, clés de pseudonymisation ; exécution sous l'identité de l'utilisateur | Niveaux 0–1 par défaut ; niveau 2 seulement pour un périmètre explicitement autorisé |
| API d'ingestion et identité, phase 4 | Jeton court, identité réelle nécessaire à l'autorisation, manifeste des dépôts approuvés ; aucune confiance dans les champs d'autorisation du client | Index pseudonymisé et extraits filtrés, après validation et second contrôle |
| Index et magasin d'extraits | Index sans texte libre ; objets d'extraits chiffrés sous des droits séparés | Lecture minimale, par équipe, rôle et finalité ; références opaques seulement vers le coach |
| Coach, évaluateur, rédacteur de PR | Coach en lecture seule sur les observations autorisées ; évaluateur privé sur ses cas ; rédacteur de PR sur les synthèses approuvées | Comptes rendus et résultats sans contenu privé vers GitHub |

Le chemin normal est `hook → travailleur local → filtrage → file chiffrée → [API phase 4] → index / objets → accès contrôlé`. Le hook n'expédie pas directement une transcription. La [référence officielle des hooks](https://docs.github.com/en/copilot/reference/hooks-reference) donne `transcriptPath` à `agentStop`, qui marque la fin d'un tour, tandis que `sessionEnd` fournit un identifiant et une raison de fin sans transcription. `postToolUseFailure` peut contenir arguments et erreur : le collecteur n'en retient que le nom d'outil normalisé et un code de statut autorisé. Les hooks peuvent manquer lors d'un arrêt brutal ou être désactivés ; le rattrapage local relit les fichiers de session encore présents. Le format interne de ces fichiers n'est pas pris pour une API stable : un parseur inconnu échoue fermé et incrémente un compteur sans exporter de texte.

## Contrat d'observation et pseudonymisation

L'unité d'ingestion est un **instantané filtré de session**, éventuellement partiel après un tour, puis mis à jour par de nouvelles révisions. Le schéma 6.1 de la proposition reste la base ; ajouter au schéma formel `event_type = session_snapshot`, `collection_level`, `policy_id`, `key_version`, `body_digest` et un état de clôture. Une version majeure inconnue, un champ inconnu, un texte libre dans l'index ou une valeur hors liste sont rejetés. Le client laisse `content_ref` à `null` ; seul le serveur lui attribue une référence après stockage de l'extrait. Les champs utiles sont :

| Groupe | Contenu normalisé |
| --- | --- |
| Identité d'événement | `schema_version`, `export_id`, `session_id` pseudonyme, `source_revision`, `body_digest`, `event_type`, `surface = copilot_cli` |
| Portée | `collection_scope`, `collection_level`, identifiant opaque de dépôt de code approuvé, `policy_id`, `key_version` ; tenant, équipe et `user_pseudonym` ajoutés par le serveur en phase 4 |
| Preuve technique | Dates UTC, état, nombre de tours, agent et skills avec source/version/hash **de la copie installée** si vérifiables, indication `observed`/`available_only`/`unknown`, versions du collecteur et de Copilot CLI |
| Contenu | Niveau 0 : compteurs et statuts ; niveau 1 : étapes et noms d'outils pris dans une liste ; niveau 2 : extraits filtrés limités en taille, séparés du corps indexé et reliés par `content_ref` opaque attribué par le magasin |

Le corps de l'observation ne contient ni chemin local, ni URL de dépôt brute, ni identifiant GitHub de l'utilisateur, ni jeton d'accès, ni argument/résultat d'outil, ni texte libre dans les niveaux 0–1. Le jeton d'authentification du transport reste uniquement dans l'en-tête protégé de la requête. Un nom d'agent ou de skill inconnu au catalogue est remplacé par `unknown`, avec un compteur, plutôt que copié tel quel. `outcome = success` exige une preuve externe vérifiable ; la fin d'une session ne suffit pas. Le serveur ne fait pas confiance à `collection_scope`, au niveau, à l'équipe ou aux déclarations d'usage envoyées par le poste : il les confronte à la politique active, et conserve la provenance comme **déclaration du collecteur**, pas comme attestation inviolable.

**Pseudonymisation recommandée :** une clé secrète propre à l'utilisateur et à la finalité « session », gardée dans le coffre de secrets du poste, calcule `HMAC-SHA-256` sur l'identifiant natif de session. Le pilote utilise une clé locale ; en phase 4, le service remet une clé propre au compte authentifié pour que deux postes de la même personne puissent produire le même pseudonyme sans transmettre l'identifiant natif. Une clé différente sert aux identifiants d'export. Le serveur calcule `user_pseudonym` à partir du sujet authentifié avec une clé tenant distincte et versionnée ; l'identité réelle et les clés restent dans un plan de contrôle plus restreint que l'index. Les dépôts admis reçoivent des identifiants aléatoires dans un manifeste de périmètre approuvé, consulté localement : une URL ou un chemin de dépôt inconnu ne part pas vers l'API. Le serveur vérifie que l'identifiant de dépôt appartient au périmètre du sujet et de l'équipe. Une collision de propriété entre équipes bloque l'export jusqu'à décision du propriétaire des données. Ces pseudonymes restent des données personnelles réidentifiables par rapprochement ou par le plan de contrôle ; ils ne sont pas anonymes.

`source_revision` est une empreinte HMAC de l'état natif lu localement ; `export_id` dérive de la surface, du pseudonyme de session, de cette révision et de la version des règles de filtrage. Le `body_digest` est le SHA-256 du corps **filtré** canonisé, hors `body_digest` lui-même et champs attribués par le serveur. Une réémission avec même `export_id` et même digest renvoie le même accusé ; même identifiant avec digest différent produit un conflit à examiner, jamais un écrasement silencieux. Le serveur conserve les révisions immuables et expose une vue logique par session ; en cas d'instantanés concurrents ou de chronologie incertaine entre postes, l'analyse les marque ambigus et ne les compte pas comme sessions indépendantes. La rotation d'une clé de pseudonymisation peut rompre ce rapprochement : garder la version de clé le temps de la rétention et documenter les ruptures lors d'une rotation d'urgence.

## Collecte, reprise et transport

- Le hook personnel, installé séparément des skills et profils, enregistre rapidement un **travail local** contenant le chemin de transcription dans la base chiffrée, puis rend la main. Un inventaire léger au début de session relève les versions et empreintes des copies installées ; il n'est pas une preuve de leur invocation. Le travailleur vérifie que le chemin appartient au magasin de sessions attendu, refuse les liens ou sorties de ce périmètre, lit un instantané stable, applique la liste d'autorisation de champs et les règles de nettoyage, puis remplace le pointeur par l'observation filtrée dans une transaction. Un échec de lecture ou de nettoyage ne met jamais la transcription brute dans la file de transmission ; il laisse un code d'échec et un compteur sans contenu. Le hook n'est pas une barrière de sécurité pour Copilot et ne doit pas ralentir sensiblement sa session.
- Le journal durable suit les états `à_lire`, `prêt`, `en_cours`, `accusé`, `rejeté` ; seuls les éléments `prêt` forment la file d'export. Le rattrapage balaye périodiquement les sources natives et réenregistre les travaux manqués. En phase 4, seuls les éléments `prêt` sont envoyés. Un accusé arrive après validation, stockage durable des objets éventuels et validation de la transaction d'index ; la suppression locale suit l'accusé. Une coupure après réception mais avant accusé cause une nouvelle tentative sans doublon. Les réponses `429` et `5xx` se retentent avec délai exponentiel et gigue ; `401` demande une nouvelle authentification ; `403`, schéma invalide ou retrait de périmètre bloque l'élément et son contenu expire selon le TTL. Une file pleine cesse d'accepter de nouveaux éléments et expose un compteur de pertes, sans exporter de brut ni casser Copilot.
- **Phase 4 seulement :** `POST /v1/observations` sur HTTPS avec validation TLS, taille maximale, version de schéma et clé d'idempotence. Un client natif obtient un jeton d'accès court auprès du fournisseur d'identité de l'organisation par code d'autorisation avec PKCE dans le navigateur système ; le secret durable éventuel est dans le coffre du poste. La référence est un jeton d'accès signé et destiné à l'API : celle-ci valide signature, émetteur, audience, expiration et autorisation active à chaque lot ; si l'organisation emploie des jetons opaques, elle utilise l'introspection de l'émetteur. Elle déduit tenant, sujet, équipe et dépôts permis du serveur, jamais d'une simple assertion du client. Aucun PAT GitHub ni `GITHUB_TOKEN` ne sert d'identité d'ingestion. [RFC 8252, OAuth pour applications natives](https://www.rfc-editor.org/rfc/rfc8252.html).
- Le serveur refait la validation du schéma et un contrôle de secrets sur les extraits de niveau 2. Il écrit d'abord les objets privés sous des identifiants non encore référencés et confirme leur durabilité, puis valide dans une transaction l'index, les références et la contrainte unique `(tenant, user_pseudonym, export_id)`. L'accusé n'est émis qu'après cette transaction ; un nettoyeur retire uniquement les objets restés sans référence. Le contrôle serveur réduit le risque, mais ne remplace pas le filtrage local : le contenu a déjà franchi la frontière réseau lorsqu'il arrive à l'API. Les corps de requête, jetons et extraits ne figurent ni dans les journaux applicatifs ni dans les traces d'erreur.

## Stockage de référence, chiffrement et accès

**Référence conditionnelle :** sur le pilote, une base **SQLCipher** locale pour le journal et la file, avec clé conservée dans le coffre du système, droits du seul utilisateur et chiffrement du disque. SQLCipher ajoute le chiffrement au format SQLite ; SQLite ordinaire ne le fait pas. Son intégration et sa licence doivent être approuvées sur les plateformes pilotes. Si un poste, notamment WSL, n'offre pas de coffre acceptable, l'export attend une solution approuvée ; il ne retombe pas en clair. [Projet SQLCipher](https://github.com/sqlcipher/sqlcipher).

Pour le collectif, une API interne avec **PostgreSQL** pour l'index transactionnel et un **stockage d'objets privé compatible S3 avec KMS** pour les extraits est un point de départ si ces services sont déjà opérés et approuvés par l'organisation. PostgreSQL facilite la contrainte d'idempotence, les recherches structurées et la filiation de suppression ; les objets permettent des droits, clés et TTL distincts pour le texte. L'API est le seul chemin de lecture/écriture applicative vers les objets. L'index ne comporte ni colonne de texte libre, ni recherche plein texte, ni embeddings d'extraits. Le volume de la base et ses sauvegardes sont chiffrés avec des clés gérées ; les objets et leurs versions sont chiffrés au repos sous des clés KMS séparées par périmètre d'équipe, avec politique de clé restrictive. Les clés et droits d'administration sont séparés des comptes d'analyse. Le chiffrement au repos ne protège pas contre un compte applicatif autorisé ou compromis.

L'API applique le refus par défaut à chaque requête. Le rôle « collecteur » ne dépose que pour son sujet et les dépôts admis ; « analyste » lit les métadonnées de ses équipes ; « lecteur d'extraits » obtient ponctuellement un objet précis pour une finalité journalisée ; « évaluateur privé » lit ses cas autorisés ; « rédacteur de PR » ne lit pas les extraits ; « opérateur suppression » agit sur les données et leurs dérivés sans droit de rédaction GitHub. Les comptes de service sont distincts. Les politiques de lignes PostgreSQL peuvent renforcer l'isolation par tenant et équipe, avec rôles non propriétaires et sans `BYPASSRLS`, mais ne remplacent pas la vérification de l'API : les propriétaires et administrateurs peuvent contourner ces politiques. [Documentation PostgreSQL : sécurité des lignes](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Les accès aux objets passent par l'API, avec autorisation, durée bornée et journal d'accès ; aucune URL publique permanente. Les métadonnées elles-mêmes restent sensibles, car dates, versions et pseudonymes peuvent révéler des habitudes de travail.

**Alternatives :** pour un très petit collectif, une base chiffrée par équipe avec objets locaux pourrait suffire si sauvegarde, contrôle d'accès et suppression sont réellement opérés ; un service managé équivalent à PostgreSQL/S3 est acceptable s'il satisfait les mêmes tests de frontières. Un entrepôt d'observabilité ou un SaaS n'est envisageable qu'après preuve de filtrage avant export, résidence, accès et suppression des copies et index secondaires. Un dépôt GitHub privé ou des artefacts Actions sont écartés comme magasin : l'historique, les clones, les caches et les journaux compliquent l'effacement. GitHub avertit que le masquage des secrets dans les journaux Actions n'est pas garanti. [Référence GitHub Actions : usage sécurisé](https://docs.github.com/en/actions/reference/security/secure-use).

## TTL, retrait, suppression et audit

Ces valeurs sont **des paramètres recommandés pour l'essai**, pas une politique déjà approuvée : travaux locaux non traités et file filtrée **7 jours** ; objets temporaires orphelins **24 heures** ; extraits de niveau 2 **30 jours** ; métadonnées niveaux 0–1 et références **90 jours** ; journal d'accès sans contenu **365 jours**. Le niveau 3 reste désactivé. Une promotion en cas d'évaluation privée crée un dérivé avec propriétaire, provenance et TTL explicites, jamais une conservation implicite indéfinie. Les durées définitives, la résidence, les plafonds de volume et les éventuelles obligations de conservation relèvent de l'organisation. Les sessions natives Copilot suivent une politique séparée.

Un retrait ou une demande de suppression authentifiée arrête d'abord la collecte locale, détruit la file correspondante et crée côté serveur une **interdiction de réingestion** liée au sujet ou à la session. L'API la vérifie avant tout accusé, pour qu'un poste resté hors ligne ne restaure pas les données plus tard. Le service masque immédiatement les enregistrements aux lecteurs, supprime index et toutes les versions d'objets, réplicas, caches, sorties du coach et cas privés dérivés selon une table de filiation, puis vérifie la purge. Les sauvegardes ont un horizon borné approuvé ; toute restauration reste isolée jusqu'au rejeu des suppressions. Ne pas promettre l'effacement physique immédiat d'une sauvegarde : documenter le délai maximal réel. Les agrégats non réidentifiants peuvent être conservés seulement si l'organisation l'autorise. Les références déjà présentes dans une PR deviennent des pointeurs expirés ; aucun contenu privé ne doit avoir été copié dans son historique. La suppression des sessions natives, locales ou synchronisées avec GitHub, suit les commandes et règles de Copilot et ne découle pas de cette purge.

Le journal d'audit, distinct des observations, enregistre horodatage, acteur ou service, rôle, finalité, type d'action, ressource opaque, décision d'accès, export, expiration et vérification de suppression. Il ne contient ni extrait, ni prompt, ni jeton, ni URL de dépôt brute. Les écritures sont append-only pour les rôles applicatifs et surveillées par un propriétaire sécurité. Un identifiant de demande permet de prouver les étapes de suppression sans réintroduire le contenu supprimé dans l'audit.

## Validation par phases

| Étape | Critères de passage |
| --- | --- |
| Pilote local, phase 0 | Deux dépôts de code distincts et un skill/profil installés volontairement ; événement conforme au schéma et dépôt pseudonymisé ; `observed` seulement avec preuve ; secret de test absent de l'index, des extraits et des journaux ; nettoyage en échec sans export ; relance du hook et rattrapage sans doublon ; session Copilot utilisable malgré une panne du collecteur ; TTL local et perte de clé testés. |
| Préproduction collective, avant phase 4 | Accord sécurité/conformité et information des utilisateurs ; authentification, retrait, dépôt hors périmètre, rôle d'une autre équipe, file hors ligne, rejet `409`, panne entre objet et index, restauration de sauvegarde et suppression des dérivés testés ; vérification que les données privées n'apparaissent dans aucun journal ou artefact GitHub/CI. |
| Extension contrôlée, phase 4 | Couverture calculée seulement sur les postes équipés ; mesures des échecs de filtrage, latence, retard et pertes de file ; revue d'accès et d'audit ; restauration avec rejeu des interdictions de réingestion ; test de rotation des clés et de révocation d'un utilisateur. |

Les jeux de test doivent inclure secrets, données métier et chemins dans chaque position de l'entrée, sorties d'outils volumineuses, session encore ouverte, fin brutale, dépôt inconnu et contenu conçu pour donner des instructions au coach. Le nombre de sessions observées et la présence d'un skill installé ne prouvent ni son invocation ni la qualité d'un changement.

## Limites, risques et choix à faire par l'organisation

- **Risque de fuite par filtrage imparfait :** les détecteurs ont des faux négatifs. Un niveau 2 exige une politique explicite, une seconde vérification et une revue humaine avant toute promotion en cas d'évaluation ou publication d'extrait.
- **Risque de couverture et de doublons :** hooks absents, désactivés, expirés ou format natif changé ; même session traitée sur plusieurs postes ou sous deux versions de clé. Suivre les pertes, isoler les parseurs par version, exclure les cas ambigus des décomptes indépendants. Une preuve cryptographique que Copilot a réellement exécuté un artefact n'est pas fournie par ce plan.
- **Risque d'accès indirect :** administrateurs des postes, de la base, des sauvegardes et du KMS peuvent dépasser les rôles applicatifs. Prévoir séparation opérationnelle, revues et tests d'accès réels.
- **Décisions organisationnelles requises :** classes de dépôts et niveaux de collecte admissibles ; base d'autorisation et procédure de retrait ; fournisseur d'identité, équipes propriétaires et cas des dépôts partagés ; services de stockage, coffre et KMS approuvés ; résidence et TTL définitifs, y compris sauvegardes et dérivés ; rôles autorisés à lire les extraits ; traitement de la synchronisation native Copilot. Aucun de ces choix n'est inféré du dépôt de cette proposition.
